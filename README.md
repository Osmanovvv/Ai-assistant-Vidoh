# ВЫДОХ

Telegram-бот, который принимает поток мыслей голосом или текстом, раскладывает его по темам, ведёт бэклог задач и доводит до одного конкретного следующего действия.

## Стек

| Слой    | Технология                                        |
| ------- | ------------------------------------------------- |
| Язык    | Node.js 24, TypeScript в строгом режиме           |
| Бот     | grammY (Bot API 9.5+ — нужны темы в личных чатах) |
| API     | Express 5                                         |
| База    | PostgreSQL 17 + pgvector                          |
| Очереди | Redis + BullMQ                                    |
| Админка | React + TypeScript                                |
| Тесты   | Vitest, Playwright                                |
| Хостинг | Docker Compose, Caddy                             |

## Требования к окружению

- Node.js 24+
- Docker и Docker Compose
- ffmpeg (в образе устанавливается автоматически)

## Запуск для разработки

```bash
npm install
cp .env.example .env      # заполнить BOT_TOKEN и остальное
npm run infra:up          # Postgres и Redis в Docker
npm run db:migrate
npm run dev
```

Вебхук Telegram требует HTTPS, поэтому локально нужен туннель (cloudflared, ngrok) — его адрес указывается в `PUBLIC_URL`.

## Локальный тестовый стенд

`docker-compose.dev.yml` поднимает только PostgreSQL с pgvector и Redis.
Бот, админка, тесты и обращения к моделям от этого не запускаются.
PostgreSQL доступен на `127.0.0.1:5434`, Redis — на `127.0.0.1:6379`.
Существующие данные сохраняются в томах `vydoh_postgres-data` и `vydoh_redis-data`.

Базы разделены по назначению:

| Назначение               | База PostgreSQL   | Переменная подключения                      |
| ------------------------ | ----------------- | ------------------------------------------- |
| Интеграционные тесты     | `vydoh_test`      | `TEST_DATABASE_URL`                         |
| Стенд админки Playwright | `vydoh_admin_e2e` | `ADMIN_E2E_DATABASE_URL`                    |
| Сквозные сценарии бота   | `vydoh_e2e`       | `E2E_DATABASE_URL`                          |
| Проверка разбора моделью | `vydoh_eval`      | `DATABASE_URL` в отдельном процессе прогона |

Подготовка интеграционных тестов, стенд админки и сквозные сценарии бота
проверяют адрес **до подключения, миграций и очистки**. Разрешены только
`localhost`, `127.0.0.1` или `[::1]`, явный порт `5434` (локально) либо `5432` (CI)
и база соответствующего сценария. Параметры URL и фрагменты не допускаются.
Логин и пароль не выводятся при отказе. Для проверки разбора используется
отдельная база: интеграционные тесты очищают таблицы, включая промпты.

Сквозные сценарии используют отдельные базы Redis: `7` для этапа 2,
`8` для этапа 3 и `9` для `check-complaint`. Интеграционные тесты используют
свои префиксы ключей и очередей.

Обычная остановка стенда — `npm run infra:down`. Команда `infra:reset`
удаляет тома вместе с локальными данными; для подготовки и остановки стенда
она не нужна. Запуск тестов и сборки — отдельный шаг от запуска хранилищ.

## Команды

| Команда                           | Что делает                                    |
| --------------------------------- | --------------------------------------------- |
| `npm run dev`                     | Запуск бота в режиме разработки               |
| `npm run build`                   | Сборка                                        |
| `npm run typecheck`               | Проверка типов                                |
| `npm test`                        | Модульные и интеграционные тесты              |
| `npm run db:generate`             | Генерация миграции по изменённой схеме        |
| `npm run db:migrate`              | Применение миграций                           |
| `npm run infra:up` / `infra:down` | Локальные Postgres и Redis                    |
| `npm run test:int`                | Интеграционные тесты (нужны Postgres и Redis) |
| `./ops/deploy.sh`                 | Выкладка на боевой сервер в один шаг          |
| `./ops/e2e-stage1.sh`             | Сквозной тест на боевом сервере               |

Миграции — только через генератор, потому что он считает разницу от последнего снимка в
`apps/bot/drizzle/meta`, а не от журнала: файл и запись, добавленные руками, оставляют снимок
позади, и следующая генерация пытается создать заново всё, что в базе уже есть. Изменилась
схема — `npm run db:generate -- --name=<имя>`; миграция без смены схемы (перенос данных) —
`npm run db:generate -- --custom --name=<имя>`, и SQL пишется в подготовленный пустой файл.
Отставший снимок ловит `apps/bot/src/db/migrations.test.ts` обычным прогоном тестов.

Качество расшифровки на конкретной записи:

```bash
SPEECH_PROVIDER=yandex YANDEX_API_KEY=... npx tsx apps/bot/src/scripts/check-speech.ts запись.ogg
```

## Выкладка

```bash
./ops/deploy.sh
```

Скрипт отправляет исходники на сервер по SSH, собирает образ, накатывает миграции и перезапускает сервисы, дожидаясь, пока бот станет здоровым. Файл `.env` на сервере не трогается.

Архив собирает отдельный скрипт `bash ops/deploy-archive.sh`. Он пишет архив
в стандартный вывод и выполняет только локальную упаковку. В состав входят
код бота и админки, `ops/`, манифесты зависимостей и конфигурация сборки.
Документы, ключи, локальные сессии, журналы, результаты проверок и резервные
архивы исключаются, в том числе внутри разрешённых каталогов. Новые локальные
исходники включаются без требования предварительно сделать коммит.

Промпты и отчёты контрольных прогонов доставляет `ops/seed-prompts.sh`
отдельным шагом; обычная выкладка проверяет активные промпты в базе.

Перед сборкой выкладка сохраняет образ существующего контейнера как
`vydoh-bot:rollback-<полный ID>`. После успешных проверок новый образ получает
метку `vydoh-bot:release-<полный ID>`. Эти метки не перезаписываются другим
образом. Сведения об образах лежат на сервере в `.data/releases/`; сервисы
при сохранении образа не перезапускаются, дополнительные слои не создаются.
Сохранённые образы нужно исключать из ручной очистки Docker.

Проверенную версию исходников фиксируем коммитом и отдельной Git-меткой;
для неё сохраняем результаты проверок и ID Docker-образа. Образ на сервере
и локальная сборка могут различаться: для отката сохраняется именно образ
работающего контейнера, а не предполагаемый аналог из локальных исходников.

План возврата можно посмотреть на сервере без изменения сервисов:

```bash
cd /opt/vydoh
bash ops/rollback.sh 'vydoh-bot:rollback-<полный ID>'
```

После отдельного согласования отката добавляется `--apply`. Скрипт
пересоздаёт только `bot`, выбирая сохранённый образ через Compose override,
с флагами `--no-build --no-deps`. База, миграции и активные промпты при этом
не восстанавливаются: их совместимость со старым кодом проверяется заранее.
Затем проверяем здоровье контейнера и ручной сценарий в Telegram.

Порядок развёртывания на чистый сервер, переход на домен и разбор инцидентов — в рантбуке (`docs/07-runbook.md`, вне репозитория).

## Структура

```
apps/
  bot/        Telegram-бот, конвейер обработки, API админки

docs/         Проектная документация (не в репозитории)
```

## Документация

Техническое задание, разбор требований и план разработки в репозиторий не входят: репозиторий публичный, а документы содержат коммерческие данные заказчика. Они ведутся отдельно.

## Ветки

- `main` — стабильная, изменения только через pull request
- `dev` — рабочая
